## Supacode / zmx terminal study (2026-07-02)

Question asked: can Kiri use the terminal supacode
(`github.com/supabitapp/supacode`) uses, instead of xterm? **Answer: no for
the emulator, yes for the persistence layer.** Supacode embeds Ghostty
natively (GhosttyKit / `ghostty_surface_t` into AppKit `NSView`s, Metal,
plus local Ghostty patches) — there is no Electron/DOM path for that, and
Kiri's server additionally depends on `@xterm/headless` + `SerializeAddon`
as the source of truth for scrollback restore, `terminal.read`, `wait-for`,
and wake delivery, so xterm would remain server-side even after a renderer
swap. The two adoptable techniques became plans 019 and 020. Neat twist:
zmx's in-daemon emulator IS `ghostty-vt` — adopting it (plan 020) brings
Ghostty's VT engine into Kiri as the durable session-state keeper, just not
as the renderer.

The same session re-audited plans 012–018 against HEAD (`1fa5160`) with
parallel codex drift auditors; all seven survived with corrections folded
into their text: 012 (daemon writes runtime snapshots nothing reads — now
eliminated at the source), 013 (`requireUnique` short-circuit analysis;
review-path generation race; hook-handler write order), 014 (PATH is
*prepended*, shim-ordering caution), 015 (archive guard extended to the full
projection surface), 016 (`resourcesByProject` is visible-projects-only —
soft dep on 018 H5), 018 (H4 must reconcile with the client's localStorage
selection restore; H6 partially documented already). One auditor finding was
rejected: `task-progress.tsx`'s remount key omitting task status is
intentional (preserves expanded UI state), not a bug.

Ship-gate review on 2026-07-02 added two executor-safety corrections:
012's spawn singleflight must resize joined callers to their requested
`cols`/`rows` and test mismatched geometry; 014 owns Claude hook writers,
`kirictl claude-hook`, and `agent.tasks.replace`, while 017 only consumes the
resulting Claude task rows.

server, backend control endpoint, lifecycle hooks) at commit `e464651`.

## Findings considered and rejected

Recorded so future audits don't re-litigate them:

- **Preferences/theme, project reorder/selection, browser/resource, and
  workspace snapshot/revision operations** (2026-07-04 parity audit) — the
  UI has them, agents don't need them; deliberately excluded from plan 023's
  scope. Revisit only with a concrete agent use case.
- **`workflow.await` reclassification as read** (2026-07-04) — rejected:
  `deliver:"wake"` registers delivery state that later injects terminal
  input (`kiri-control.ts:663`); the conservative write classification
  stands. `terminal.wait-for`/`workflow.validate` reclassification is
  planned (021).
- **Per-operation MCP tools instead of `kiri_get`/`kiri_do`** (2026-07-04)
  — rejected for now: 45 tools would bloat every agent's tool list; the
  two-tool funnel plus schema-backed `operations.list` (plan 023) keeps
  discovery cheap without the bloat.

- **SSR layer per request** — investigated; the Effect layer is already a
  process-level singleton and SSR cost is initial-load only. Not a hot path.
- **Terminal panel / registry session leaks (LEAK-08, LEAK-09)** — cleanup
  verified correct: `terminal-panel.tsx` cleanup disposes socket handlers,
  observers, addons, and the terminal; `terminal-registry.ts` `exit()`
  deletes and disposes sessions. Only the daemon-level maps leak (plan 004).
- **Client snapshot dedupe via `JSON.stringify` fingerprint** — real cost,
  but after plan 001 gates the action poll it leaves the hot path entirely.
  A structural-compare rewrite is risk without payoff; deferred (noted in
  plan 001).
- **Daemon `agents` map eviction** — rejected: deleting entries on
  close-runtime would break wake-delivery respawn (`spawnForDelivery` needs
  the retained launch config). Documented as out-of-scope in plan 004.
- **`maxBuffer` 10MB on the Rust indexer call** — guardrail only; no
  evidence of it being approached.
- **One-tick revision lag (DATA-09)** — the revision gate can serve a
  snapshot one tick stale; acceptable by design for a 2s poll.
- **Electron window-before-backend startup ordering** — the window is
  `show: false` until `loadURL` completes, so reordering alone changes
  nothing perceptible; a real fix means a splash/loading state, which is a
  product decision. Recorded in plan 006's maintenance notes.
- **Shrinking the 10k terminal scrollback default** — product trade-off
  (users want scrollback), not a clear win. Knob exists at
  `terminal-registry.ts:91` if ever wanted.
- **Claude-session hydration cache** — same shape as plan 002's Pi cache;
  worth doing as a follow-up to 002 using the identical stamp pattern, but
  not planned now to keep 002's scope tight.
- **`@pierre/diffs` importing full `shiki` instead of `shiki/core`** — the
  9.4MB grammar payload is an upstream packaging issue; plan 006 defers the
  cost via lazy-loading, and the upstream fix is recorded in its
  maintenance notes.

## Direction / backlog (not planned — bigger than a plan file)

- **Push instead of poll**: an SSE or WebSocket push channel from the
  backend for workspace changes would eliminate the 2s background poll and
  the 750ms action-window poll entirely. Plans 001–003 make polling cheap;
  push makes it unnecessary. L effort, touches client+server contract.
- **Fully self-contained server bundle**: bundle srvx/effect/ws/
  xterm-headless into `dist/server`, keep only `node-pty` external, and
  drop node_modules from the asar almost entirely. Sized as the follow-up
  to plan 008 (see its maintenance notes).
- **Shared MCP process**: each agent session currently gets its own
  kiri-mcp process; a shared instance would cut per-session RSS. Needs
  design for session identity and lifecycle.
